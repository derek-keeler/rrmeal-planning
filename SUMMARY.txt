ARCHITECTURAL DECISIONS
================================================================================

Architecture Pattern:
  - Hexagonal/Layered Architecture
  - Domain → Application → Infrastructure → API
  - SOLID principles throughout

Core Entities (9):
  1. FamilyMember - Household members with preferences
  2. Ingredient - Food items with nutrition
  3. Recipe - Complete recipes
  4. RecipeIngredient - Junction with quantities
  5. MealPlanWeek - Weekly plan container
  6. Meal - Specific recipe instance
  7. MealRating - Thumbs up/down ratings
  8. ExternalFoodEntry - Imported data
  9. LLMGeneration - AI audit log

Key Use Cases (7):
  1. CreateRecipeUseCase
  2. GenerateMealPlanUseCase
  3. RateMealUseCase
  4. ImportMyFitnessPalDataUseCase
  5. GenerateLLMRecipeUseCase
  6. ListRecipesUseCase
  7. GetMealPlanWeekUseCase

Technology Stack:
  - Python 3.11+ with type hints
  - FastAPI for REST API
  - SQLAlchemy 2.0+ ORM
  - Alembic for migrations
  - SQLite (dev) / PostgreSQL (prod)
  - pytest for testing
  - Docker for deployment
  - GitHub Actions for CI/CD

================================================================================
KEY FEATURES
================================================================================

Intelligent Meal Planning:
  - 80% repeat meals (from highly-rated recipes)
  - 20% new meals (LLM-generated or unexplored)
  - Variety constraints (4-week lookback)
  - Locked meal support

Rating System:
  - Thumbs up/down per family member
  - Aggregate logic: >3 thumbs = highly rated
  - Used to select repeat meals

External Integrations:
  - MyFitnessPal import (CSV/JSON)
  - LLM recipe generation (OpenAI/Anthropic)
  - Graceful fallback when services unavailable

Family Support:
  - Multiple family members
  - Dietary restrictions per member
  - Allergies and dislikes tracking
  - Meal participation tracking

================================================================================
DESIGN PRINCIPLES (SOLID)
================================================================================

✅ Single Responsibility: Each component has one purpose
✅ Open/Closed: Extend via interfaces, not modifications
✅ Liskov Substitution: Implementations interchangeable
✅ Interface Segregation: Small, focused protocols
✅ Dependency Inversion: Depend on abstractions
